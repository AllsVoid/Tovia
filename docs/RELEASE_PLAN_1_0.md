# Tovia 所至 — 1.0 分版本发布计划

状态基线：2026-09-20
目标：以可验证、可回滚的小版本逐步完成 Tovia 1.0，避免跨阶段同时修改数据模型、核心交互与 AI 流程。

本文是 1.0 范围和完成状态的唯一发布基线。PRD 描述产品目标，DATA_MODEL 和 API_SPEC 描述实现约束；当范围或完成状态发生变化时，先更新本文，再更新对应设计文档。

## 1. 版本规则

- 每个版本只在前一版本验收通过后开始收口；可以提前做技术调研，不提前发布依赖未完成的数据能力。
- `已完成` 只表示代码、迁移、文档和该版本验收全部通过。仅有界面、接口或模型之一时仍记为 `进行中`。
- AI 只产生 Candidate，必须由用户确认后才能写入 Booking、Expense、Activity 等正式实体。
- Place、Visit、Trip 的既有边界保持不变：Place 是规范地点，Visit 是一次实际或计划到访，Trip 是容器。
- 所有新增实体继续使用 UUID、时区明确的时间、Decimal 金额和用户级数据隔离。
- 每个版本都要更新本文的状态、完成日期、验证结果链接和遗留问题。

状态取值：`已完成`、`进行中`、`未开始`、`阻塞`。

## 3. v0.2 — 地图与日历基础

状态：**已完成**
完成日期：2026-09-20
对应原 Roadmap：Phase 0–2

### 已完成

- Next.js、FastAPI、PostgreSQL、PostGIS、Alembic 与 Docker Compose 基础工程。
- User、Trip、TripDay、Place、Visit、Activity、WishlistItem 核心模型与 API。
- 创建、编辑和删除旅行；添加旅行日和活动。
- 新建旅行后添加城市并生成 Visit；地图不再要求用户输入经纬度。
- 国内市级行政区、海外国家级区域高亮；曾至、将至、未至筛选。
- 月历、当天详情以及“城市 → 到访 → 活动”树状展示。
- 同一 Place 支持多次 Visit；删除 Trip 时保留访问事实。
- 基础错误、加载、空状态、桌面与窄屏布局。
- 静态检查、真实 PostgreSQL/PostGIS 集成测试、迁移往返和浏览器流程测试。

### 保留问题

- 只有开发身份，不能用于生产登录。
- Visit 和 Activity 在 Web 中缺少完整编辑能力。
- Inbox 与 Profile 仍是占位页面。
- Booking、Expense、Document、Photo、AI Candidate 和 Memory 尚未实现。

验证记录见 [VERIFICATION.md](VERIFICATION.md)。

## 4. v0.3 — 数据可维护与正式身份

状态：**进行中**
目标：先让现有旅行数据可安全保存、纠正和迁移，再增加新的业务模块。

Logto 正式身份采用渐进式接入，分阶段范围、回归门槛和回滚点见 [AUTH_LOGTO_ROADMAP.md](AUTH_LOGTO_ROADMAP.md)。任何阶段不得默认改变现有 development 身份或一次性引入完整账户平台。

### 阶段进度

- 阶段 A 已完成（2026-09-20）：建立与身份厂商无关的认证凭证、主体契约和配置边界；补齐 API 认证保护与现有开发身份的回归测试。此阶段没有引入 Logto SDK、OIDC 运行模式、数据库迁移或登录界面，现有运行行为保持不变。
- 阶段 B 已完成（2026-09-20）：新增本地 `UserIdentity` 映射、唯一约束、向前兼容迁移和显式运维绑定命令；真实 PostgreSQL/PostGIS 验证原有 User/Trip UUID 保持不变。请求认证仍只使用 development provider。
- 阶段 C 已完成（2026-09-20）：增加默认关闭的 OIDC Bearer provider，只允许 Logto 默认的 ES384 和密钥轮换可用的 RS256，并校验 JWKS 签名、issuer、audience、expiry 和 subject；只解析已绑定的本地身份，不自动注册。浏览器登录仍未接入。
- 阶段 G 实现完成，待真实环境验收（2026-09-22）：API production 仅允许 OIDC、公开 issuer 强制 HTTPS；Web production 启动时要求 OIDC、HTTPS endpoint 和完整密钥；JWKS 连接故障 fail-closed 并返回 503；认证成功、凭证拒绝和身份映射冲突写入带 request ID 的 JSON 审计日志。隔离 PostGIS 的自动备份恢复演练已通过；真实 HTTPS/Logto 部署和应用回滚演练尚未执行，故 v0.3 仍未完成。
- 数据维护工作包实现完成（2026-09-22）：Profile 可编辑显示名称、时区和语言；JSON 导出涵盖当前用户全部已实现实体并保留 UUID/关联，并提供独立离线校验命令检查 schema、时间和引用；Visit、Activity、TripDay 可在 Web 修正；Logto 账户删除需要 prompt=login、5 分钟内签发的 token、二次文字确认及 API 服务端 Management API 配置；导出和关键删除均记审计。PostGIS 集成测试与迁移往返通过；真实 Logto Management API 删除、双账户浏览器流程和生产环境运维演练仍未执行。
- 后续阶段按 [AUTH_LOGTO_ROADMAP.md](AUTH_LOGTO_ROADMAP.md) 逐步实施；每阶段独立验证和回滚，不跨阶段预装组件。

### 必须实现

- 正式 AuthProvider：登录、退出、会话校验和过期处理。
- Profile 基础页：显示账户信息、导出数据、删除账户入口。
- 所有业务接口验证当前用户所有权；客户端不得指定或切换 `user_id`。
- Visit 编辑：抵达时间、所属 Trip、TripDay、备注。
- Activity 编辑：标题、日期、所属城市、时间、类型和备注。
- TripDay 编辑：日期与主题；日期改变时明确处理活动和 Visit 关联。
- JSON 全量导出，包含版本号、实体 ID 和关联关系。
- 最小审计记录：登录异常、数据导出、账户删除和关键实体删除。
- 将 Inbox/Profile 占位状态改为真实页面或在功能可用前移除无效入口。

### 验收

- 两个真实账户的数据完全隔离，跨用户读取、修改和删除均返回 404 或 403。
- 用户可以纠正一条错误 Visit 和 Activity，无需删除后重建。
- 导出文件可通过验证脚本检查引用完整性、时间与金额格式。
- 生产配置不能启用开发身份；无有效会话时所有业务接口返回 401。
- 新库安装、从 v0.2 升级、数据库备份与恢复演练通过。
- Profile 导出文件可校验所有已导出记录的 ID 与引用；账户删除在真实 Logto 环境验证重新认证、身份删除和本地数据清理结果。

### 本版本不做

- 第三方社交登录组合。
- 复杂角色与多人协作。
- Booking、文件上传和 AI。

## 5. v0.4 — Booking 与 Expense

状态：**未开始**
依赖：v0.3

### 必须实现

- Booking 模型、迁移、CRUD 和旅行详情视图。
- 支持 Flight、Train、Bus、Hotel、Ticket、Restaurant、Other。
- 交通和住宿的关键时间、地点、确认号、状态与备注。
- Expense 模型、迁移、CRUD 和旅行详情视图。
- 原币金额、原币币种、结算金额、结算币种、实际汇率、类别、支付方式、日期、地点和 Trip。
- 金额统一使用 Decimal；不通过浮点数计算汇总。
- Trip Summary：预订数量、总花费、按币种和类别分组；不虚构实时汇率。
- Booking/Expense 与 Trip、Place、Activity 的关联边界和删除策略。

### 验收

- 可手工完整记录一次包含往返交通、住宿和多笔消费的旅行。
- 修改或删除 Trip 时不会产生悬空 Booking/Expense；删除行为有明确确认文案。
- 多币种金额按原始数据准确保存，汇总规则有单元与数据库测试。
- API 权限、分页、边界值和并发修改冲突测试通过。

### 本版本不做

- 自动汇率服务。
- OCR 自动录入。
- 预算优化或推荐。

## 6. v0.5 — Upload、Inbox 与 Photo

状态：**未开始**
依赖：v0.3；与 v0.4 的正式实体关联

### 必须实现

- S3-compatible StorageProvider 与本地开发实现。
- Document 模型：原始文件、MIME、大小、SHA256、storage key、来源和处理状态。
- Photo 模型：原图、缩略图、EXIF 时间、GPS、SHA256、pHash。
- 签名上传与下载；文件大小、扩展名和实际 MIME 校验。
- Inbox：上传、处理中、待处理、失败和已完成状态。
- Document/Photo 与 Trip、TripDay、Place、Booking、Expense 的可编辑关联。
- 重复文件检测；删除数据库记录时采用可恢复的文件清理策略。
- 异步队列和 Job 状态，用于 EXIF、缩略图与后续 OCR。

### 验收

- 可上传截图、PDF 和照片，刷新或重启服务后原始文件仍可访问。
- 未授权用户无法读取、枚举或覆盖其他用户文件。
- 超大文件、伪造 MIME、重复文件、处理中断和任务重试有明确结果。
- 照片能按日期和地点进入旅行时间线；缺少 EXIF 时允许用户补充。
- 数据库恢复后可以核对对象存储引用，孤立对象可被审计而非立即误删。

### 本版本不做

- OCR 内容理解。
- 自动创建正式 Booking 或 Expense。

## 7. v0.6 — OCR / AI Candidate

状态：**未开始**
依赖：v0.4、v0.5

### 必须实现

- OCRProvider 与 AIProvider 接口，业务服务不直接依赖厂商 SDK。
- Document 处理流水线：OCR、分类、结构化提取、匹配、Candidate。
- ImportCandidate 保存来源文档、提取字段、置信度、处理版本和错误信息。
- Review UI：原文/原图与候选字段并排查看，支持编辑、确认和拒绝。
- 确认后才创建 Booking、Expense 或 Activity；操作保持幂等。
- 保存 OCR 原文、确认前后差异和审核人；失败任务可重试。
- 对提示词和日志做用户数据隔离，记录 Provider 延迟、错误率和成本。

### 验收

- 机票截图、酒店订单和至少一种票据各有一组固定评测样本。
- AI 误识别不会直接污染正式数据；拒绝 Candidate 不创建任何正式实体。
- 重复确认、任务重试和页面刷新不会生成重复 Booking/Expense。
- 用户可以追溯每个正式实体来自哪个文件、哪些字段被修改。
- 识别准确率按字段报告，不只报告整体成功率。

### 本版本不做

- AI 自动制定完整旅行。
- 未经确认的后台自动写入。
- 通用聊天机器人。

## 8. v0.7 — Timeline 与 Memory

状态：**未开始**
依赖：v0.4–v0.6

### 必须实现

- Trip Timeline：按当地日期和时间聚合 Visit、Activity、Booking、Expense、Photo 和 Note。
- 同城内容保持“城市 → 活动/资料”层级；跨时区记录显示来源时区。
- 完成旅行后的 Memory 页面：路线、每日记录、照片、花费、亮点和备注。
- 允许用户选择封面、隐藏条目和修正排序，不由 AI 自动覆盖事实。
- 日历照片缩略图与 Trip 完成状态联动。
- Memory 数据来自正式实体，可追溯到原始资料。

### 验收

- 一次跨城市、跨时区旅行能得到稳定且顺序正确的 Timeline。
- 删除或编辑底层实体后 Timeline 与 Memory 一致更新。
- 无照片、无费用或只有一天的旅行都有可用空状态。
- 桌面和手机均可完成从地图/日历进入 Memory 的回看流程。

### 本版本不做

- 自动发布到社交平台。
- PDF Travel Book。
- 公共分享页面。

## 9. v0.8 — Beta 稳定性

状态：**未开始**
依赖：v0.7

### 必须实现

- 统一加载、错误、空状态和危险操作确认。
- 结构化日志、request ID、job ID、错误追踪和基础指标。
- 上传失败率、队列积压、API 错误率和 AI 成本监控。

### 验收

- 断网、数据库不可用、对象存储不可用和任务失败时有可恢复提示。

## 11. v1.0 — 正式发布

状态：**未开始**
依赖：v0.9 Release Candidate 验收通过

### 发布内容

- 用户可以登录并安全管理自己的旅行数据。
- 创建 Trip，添加城市、日程和活动，在地图与日历中查看。
- 手工记录 Booking 与 Expense。
- 上传并保留截图、PDF 和照片原件。
- OCR/AI 生成 Candidate，用户审核后写入正式实体。
- 在 Timeline 与 Memory 中回看完整旅行。
- 导出和删除个人数据。

### 发布后最低保障

- 数据库和对象存储定期备份，恢复流程定期演练。
- 错误率、任务积压、存储、AI 成本和健康状态有告警。
- 数据模型变更只通过 Alembic；破坏性迁移必须先提供备份和回滚方案。
- 1.0.x 只修复缺陷、安全和兼容性问题；新业务能力进入后续版本计划。

## 12. 每个版本的完成清单

版本只有同时满足以下条件才能标记为 `已完成`：

1. 功能和明确的异常路径已实现。
2. 数据模型、迁移、API、Web 和权限规则一致。
3. PRD、DATA_MODEL、API_SPEC、开发与验证文档已更新。
4. Ruff、格式、MyPy、Pytest、ESLint、TypeScript、Prettier 和 production build 通过。
5. 涉及数据库的版本在真实 PostgreSQL/PostGIS 上完成集成和迁移往返测试。
6. 核心用户流程有浏览器测试；发布候选必须连接真实后端。
7. 窄屏、错误、空状态和危险操作经过人工检查。
8. 本文记录完成日期、验证证据和仍然接受的限制。
